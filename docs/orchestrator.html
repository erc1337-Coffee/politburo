Orchestrator

Takes ready tasks from the board, runs each attempt in a Claude cloud session through the relay, decides after every round and publishes the work.

Main loop

All work runs on one serial chain: ticks and relay telemetry never run at the same time. Wake requests that arrive while a tick waits are merged into it.

Admission

Candidates are all ready tasks of all channels. Tasks with a live attempt are skipped. Order: priority (urgent, high, normal, low, lowest), then task number.

Plan of an attempt

  • Repository. The channel's repository setting, which must be a https://github.com/owner/name URL. A channel without one uses its local repository local:<channel>, made on first use with one empty commit on main.
  • Model routes. The party file's routes (tiers.models.sprite.routes). When the channel enables routes, only those are used, in party order.
  • Base. GitHub: the default branch head. Local: main.
  • Claim. tasks.claim with a lease of board.lease_seconds (900 s), renewed every third of it.

A task that cannot start gets one status reply not started. <reason>: the repository is not on github.com, the channel enables no party route, or all attempts are used.

Decision after a round

Fixed rules, in order

Round endStep
completed, all checks pass, no file changedcomplete: the worker's answer is the result
completed, all checks pass, files changedpublish
completed or failed, a check failsinstruct: next round with the check output (last 1500 characters each)
failed, no failing checkretry: new attempt
stoppedfail
timeout, idle, lost_contact, token_expired, worker_errorretry

Limits

  • publish without a head commit or a verified bundle becomes retry.
  • instruct at the round limit, over the wall time or over budget becomes retry while attempts remain and the budget holds, else fail.
  • retry at the attempt limit or over budget becomes fail.
  • Task cost is the sum of the worker-reported cost_usd of all attempts. Budget: limits.task_budget_usd (10).

Final decision

Runs when KEV_URL or ORCHESTRATOR_DECISION_MODEL is set, the round completed, and the step is publish, complete, or instruct because of failing checks.

LabelEffect
PASSThe fixed-rules step is applied: publish or complete.
FOLLOWUPThe step is applied. After a publish, merge or completion, up to 3 new tasks are created in the same channel, labelled politburo.followup_of and politburo.followup_depth. Not offered at depth decision.followup_depth (3).
RETRYNext round with Claude's correction as the instruction, within the limits. Not offered when no round is left.
REVIEWWork with changes is kept (draft PR, or the task branch of the local repository with main unchanged). The task is put on hold for a person.
  • Kev. POST <KEV_URL>/v1/systemone with the brief (1200 characters), the worker summary (1800), the change counts and the check results. Its PASS or REVIEW is final at confidence ≥ decision.kev_confidence (0.75). Timeout 120 s; an error counts as no answer.
  • Claude. claude --print --model $ORCHESTRATOR_DECISION_MODEL without tools, with a JSON schema: label, reason, correction (for RETRY), follow-ups (for FOLLOWUP). Kev's answer is passed as first opinion. Timeout 300 s; a failure gives REVIEW.
  • No Claude. Kev unsure gives REVIEW. No Kev and no Claude gives PASS.
  • After failing checks. No round left gives REVIEW. Otherwise Claude chooses RETRY or REVIEW; without Claude the check output becomes the correction.

The decision is stored as the task label politburo.decision and shown in the thread as a final_decision@1 block. A task that fails, is held or is lost without a model decision gets REVIEW by the rules.

Thread output

  • Round report. One reply per round with a worker_activity@1 block: thinking, tool calls, output, messages, errors and warnings (newest 60), then the changes, the checks and the worker's answer. Edited at most every 5 s while the round runs.
  • Status lines. Short replies labelled politburo.status=orchestrator: attempt started, round sent, PR opened, merged, lost, failed.
  • Questions. Pi's question is posted as a status line. The first reply of a person after it is the answer.

Messages in task threads

The orchestrator reads every message a person writes in a task thread, in any task state. Its own replies, status lines and blocks are not read. While Pi waits for an answer to its question, the first reply is that answer and goes only to the worker.

The orchestrator model (ORCHESTRATOR_DECISION_MODEL) receives the facts and answers in a fixed format. Without the model, messages are not read.

  • Facts. The task (state, brief, result, decision), its attempts, the live worker's state and phase, the pull request with its merge state and the checks of its head commit, the last 20 thread messages, and the new message.
  • Reply. The answer to the person, posted as a thread message with the outcome of each action and of the work.
  • Actions, only those that apply now: pr_ready (a draft pull request), pr_merge (squash unless the person names merge or rebase), pr_close, pr_reopen (closed, not merged), task_cancel (also stops the worker), task_retry (no worker runs).
  • Work. Code changes go to the worker. A live worker gets an instruct command with mode steer or follow_up for its running Pi. Otherwise the work becomes a follow-up request: the orchestrator reopens the finished task, or unblocks a held one, and admission starts a new attempt.

Follow-up attempt

  • Brief. The task text, then the follow-up requests, oldest first.
  • Branch. With an open pull request: its branch, from the branch head. After a merge or a close: a new branch claude/task-<N>-<K> from the default branch. A local channel repository: the task branch when main does not contain it, else main.
  • Session. When the attempt goes on from the previous attempt's work, the orchestrator sends the prompt to the previous cloud session with claude -p … --cloud <session>. A paused session resumes on the same machine, with Pi installed and the earlier worktree.
  • Attempts. Each follow-up request gives the task its attempts again: attempts before the newest request do not count.

Railway services

Railway is off for a channel until a project is chosen in the Railway tab of the channel settings. The orchestrator holds RAILWAY_TOKEN and calls the Railway GraphQL API outbound; the board and workers never get it. Only the project's production environment is used.

  • Services. Status, domains and the latest deployment of each attached service, every 15 s while the tab is open. Start, stop, restart, redeploy and rollback. Deploy and build log lines, read only while shown. Attach services of the project, or create one from the channel's GitHub repository.
  • Variables. Read when the subtab opens; values go through the board server to the orchestrator and are not stored on the board. A save sets the changed variables.
  • Settings. Root directory, builder, Dockerfile, build, start and pre-deploy commands, health check, restart policy, replicas, region, sleep, cron schedule and watch patterns of each service.

Nothing is deleted. A variable removal, or any removal a person asks for, becomes a task with the label politburo.attention, blocked for a person; the orchestrator never claims it. A service for a channel without a GitHub repository is refused the same way: the task asks for a private repository first.

Each action posts a status line in the channel. In a channel with Railway services, the orchestrator model also reads the channel chat: it answers from the services' status and log tail, does restarts and deploys, and makes a new task for code work.

Spend ledger

Each round's result.models rows go to /ledger/ledger.sqlite: provider, model, input and output tokens, and the worker-reported cost in USD. The board's usage view reads this file.
