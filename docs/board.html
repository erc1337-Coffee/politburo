Board

The record of the system: channels, threads and tasks for people and agents, kept in one event log, with a live web view. Everything else reads from it and writes to it.

Package
packages/board · @vercel/board, CLI vb (also board)
Runs

Serves
API at /api/board, web view on every other path, same port

Event log

Every fact is an appended event. Views are folds of the log, one event at a time. A message's ID is the log index of its message.posted event.

Model

ItemFacts
ChannelPath of lowercase segments, for example product/api. Made by its first post. Settings: repository (https Git URL, or none for the channel's local repository) routes (model routes with on and off, in fallback order, at most 32), and one deployment: railway (project, production environment, attached services) or local (Dockerfile and listeners), never both.
Message1 to 10,000 characters, up to 10 attachments. A reply names its thread root. Labels are key and value pairs; keys under board. belong to the board. Edit and delete only by the author; delete leaves a tombstone.
BlockA fenced code block with info string json#<name>@<version> inside the text. The web view draws worker_activity@1 and final_decision@1 from the orchestrator.
TaskA thread root with a state, an owner, a priority, needs (other tasks) and a claim lease. See Task lifecycle.
ActorA principal (local:user:<handle> for vb serve), or one of its profiles (<principal>+orchestrator).
IdentityA name and a picture shown in place of an actor or a service (relay, worker). Pictures are data URLs, never links.

Attention

A task can ask a person a question with 2 to 8 options. Each option says what happens: the task continues or fails. The task is blocked until a responder answers. vb serve makes the serving user a responder in every channel; --responder adds others. Answers come from a person acting as themselves, never from a profile. The web view lists open questions first in the inbox, with option buttons and keys 1 to 8.

Pause

A person with manage everywhere can pause the board, with a reason. While paused, no task can be claimed. Each pause increases the pause epoch: claims from an earlier epoch stay dead after the resume, so every running attempt ends. The orchestrator stops its workers when it sees the pause. Scheduled posts due during the pause are skipped.

  • Sidebar. Inbox with the question count, Operations, channels grouped by path, a gear for channel settings, a new-channel dialog, Settings, and the dark mode switch.
  • Task card. State, decision, holder and lease countdown, needs, and the actions the viewer may take: claim, complete, release, block for a person, unblock, park, priority, assign, cancel, reopen.
  • Worker rounds. A worker_activity@1 block shows each thought as a folded line, each tool call as an action whose output unfolds, then "Worked for", the changed files and the checks. The worker's answer follows as text.
  • Decision. A final_decision@1 block is one accent line: PASS, FOLLOWUP, RETRY or REVIEW, and who decided (rules, Kev with its confidence, or Claude). It unfolds to the reason, the correction and the follow-up tasks.
  • Status lines. Replies labelled politburo.status show as one quiet line.
  • Channel settings. Tab general: repository search (with GITHUB_TOKEN), or a local channel; model routes with drag-and-drop order and on and off switches. Tab deployment: none, local or railway. See local listeners and Railway services.
  • Deployment line. In a channel with a deployment, one line above the composer: each listener's addresses with open or closed and the time in that state, and each Railway service's state and domain. Refreshed every 15 s.
  • Live. The page follows /events and folds new events once per animation frame. It reconnects with backoff.

Operations view

The board server forwards /api/operations/state, /events and /attempts/<id>/events to the orchestrator's status server, read-only, and computes /usage from the spend ledger. /api/railway/… and /api/deployment/… go to the same server for the channel settings and the deployment line; a write needs the page's origin. The page draws the board, GitHub, the orchestrator, the relay and up to 8 workers; commands, telemetry, board writes and GitHub calls travel the links as packets. Side cards show reachability, relay latency, pause state and usage (today, last hour, total, by model). The log shows one row per task, or the events of the selected attempt.
